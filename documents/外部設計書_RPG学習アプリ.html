1. 文書概要

1.1 目的

要件定義書で決めた「何を作るか」を、利用者から見える形（画面・操作・外部とのやり取り・システム構成）に落とし込む。内部設計（プログラム構造・テーブル定義の詳細）の入力とする。

2.1 方式の選定理由

2026-10-27 に、AWS からさくらのクラウドへ切り替えた。AWS アカウントで Amazon Bedrock（全モデル）と AWS Lambda が使えなくなり、復旧の見込みが立たなかったため。

観点 判断
データの置き場所 さくらのクラウドは国内の事業者・国内のデータセンター。学習者の説明文を含め、すべてのデータを国内に置ける
規模の変動 パイロット約10名はサーバー1台で足りる。全社約1,000名では、サーバーのプランを上げるか、API のコンテナを増やす（Phase 3）
コスト 月額の固定費（サーバー・DB）が中心で、見通しが立てやすい。AI は使った分だけ（2.9）
運用 サーバーの OS は自分たちで更新する。アプリはコンテナにまとめ、docker compose だけで入れ替えられるようにする
移し替えやすさ DB・ファイル・メール・AI・ログインを「差し替え口」にしてあるため、AWS や別のクラウドにも移しやすい（詳細設計書 3.6〜3.10）

2.4 コンテナの役割の分担

AWS 版の Lambda 4関数は、2つのコンテナにまとめた。中の処理（ルーティング・採点・抽出・日次処理）は AWS 版と同じものを使う。

コンテナ 起動のきっかけ 処理 AWS 版での担当
api（ROLE=api） 画面からのリクエスト 画面の配信、API 全般、ログイン（4.11）。四肢択一の正誤判定、軽量モデルでのひとこと生成。採点・取り込みはジョブキューに入れる CloudFront・API Gateway・api-handler・Cognito
worker（ROLE=worker） ジョブキュー（DB）と時刻 キーワード説明の採点、PDF・画像・テキストからの問題の抽出、日次処理、30分ごとのメール送信 grading-worker・import-worker・batch-runner・SQS・EventBridge Scheduler
  • 1台で足りる間は、api と worker を同じサーバーで動かす。どちらも同じコンテナ（イメージ）で、環境変数 ROLE で役割を変える
  • 採点は同時に2件、取り込みは同時に1件まで処理する（AI の使いすぎを防ぐ）

2.5 説明採点の非同期方式

採点は30秒近くかかることがあるため、受付と処理を分ける。画面は2秒ごとに結果を確認し、その間AIパートナーの待機演出を表示する（AWS 版と同じ）。

  • 受け入れ確認の間は dev に新しい版を入れず「凍結」する。確かめた版にタグを付けて prod に配置する（詳細設計書 11.1）

2.8 AIモデルの使い分け

AI の呼び出しは「差し替え口」（詳細設計書 3.6）を通し、環境変数 AI_PROVIDER で呼び出し先を切り替える。当面はさくらのAI Engine を使い、Amazon Bedrock が使えるようになりしだい Bedrock に戻す。

用途 さくらのAI Engine（当面） Amazon Bedrock（戻したあと） 呼び出し元
問題・キーワードの抽出 gpt-oss-120b Claude Sonnet worker（取り込み）
キーワード説明の採点 gpt-oss-120b Claude Sonnet worker（採点）
四肢択一の解説コメント・パートナーのひとこと gpt-oss-120b Claude Haiku api
四肢択一の正誤判定 AI不使用 AI不使用 api
  • さくらのAI Engine は国内のデータセンターで推論する（さくらインターネットの説明）。送ったデータの扱い（学習に使われないこと）は構築時に利用規約で確認し、記録を残す
  • gpt-oss-120b は PDF・画像をそのまま読めない。そのため当面は、PDF は文字を取り出してから渡し、画像の取り込みは使えない（管理者には「テキストかPDFで取り込んでください」と出す）。文字のない（スキャンした）PDF も取り込めない。Bedrock に戻すと、PDF・画像をそのまま読めるようになる
  • 採点の質は Claude より下がる可能性がある。パイロットの前に、過去問を使って採点の結果を Claude（AWS 版の試験の結果）と見比べ、合格の基準（60点）や指示文を見直すかを決める（10 未決事項 No.12）
  • Bedrock に戻すときのモデルIDは、そのときに東京リージョンで使えるものを確かめる（AWS 版の外部設計書 2.8 の方針。推論プロファイルを使うかは未決事項 No.2）

6.2 メール送信の方式

学習者が送信時刻を選べるため、メールは1日に何度も送る。送信の処理を軽く・やり直しやすくするため、次の方式にする（AWS 版で DB の自動停止と両立させるために決めた方式を、そのまま使う）。

  1. B-01（0:00）で、通知オンの学習者ごとに「送信時刻・宛先・復習数・クエスト」を作る
  2. 送信時刻ごとのファイル（例：notify/2026-10-20/0730.json）にしてオブジェクトストレージに置く
  3. B-03（30分ごと）は、その時刻のファイルだけを読んで SMTP で送る。DBにはアクセスしない
  • 0:00より後に通知設定を変えた場合は、翌日の送信から反映する（S-10に注記を表示）
  • 送信に失敗した宛先は1回だけやり直し、結果をログに記録する
  • 定期処理は worker コンテナが時刻（Asia/Tokyo）を見て動かす。同じ枠を二重に動かさないよう、動かした枠を DB に記録する。worker が止まっていた日は、起動したときにその日の日次処理を動かす

USERS 利用者ID、ログイン用の識別子（sub）、パスワードのハッシュ、仮パスワードの期限、ログイン失敗の回数、氏名、ニックネーム、メール、状態（招待中・有効・論理削除）、削除予定日、パートナー種別、パートナー名、累計EXP、レベル、連続学習日数、最終ログイン日時
COURSES コースID、コース名、資格名
ENROLLMENTS 利用者ID、コースID、受講開始日
QUESTIONS 問題ID、コースID、問題文、正解、解説、状態（下書き・要確認・公開済み）、取り込みID
KEYWORDS キーワードID、問題ID、キーワード
ANSWER_LOGS 利用者ID、問題ID、キーワードID、形式、正誤、点数、説明文、復習かどうか、解答日時
REVIEW_ITEMS 利用者ID、形式（択一・説明）、問題ID または キーワードID、段階（0〜6）、次回予定日
GRADING_JOBS 採点ID、状態（採点中・完了・失敗）、結果JSON、作成日時
EXP_LOGS 利用者ID、コースID、理由、EXP、獲得日時（週間ランキングの元データ）
WEEKLY_RANKINGS コースID、週の開始日、利用者ID、週間EXP、順位、ニックネーム（確定時点）
PARTNERS 性格（encourage・logic・rival）、初期名、画像のオブジェクトストレージのキー（なければ空）
NOTIFY_SETTINGS 利用者ID、メール通知オン／オフ、送信時刻、プッシュ通知オン／オフ（Phase 2）
AUTH_REFRESH_TOKENS・PASSWORD_RESETS リフレッシュトークン・再設定リンクのハッシュ、利用者ID、期限、使った日時（値そのものは保存しない）
JOBS・SCHEDULE_RUNS 採点・取り込みのジョブキュー（状態・回数・やり直しの時刻）、定期処理を動かした枠

7.3 保持期間

データ 保持
学習履歴 利用者が有効な間は永続。物理削除時にすべて削除
ランキング履歴 永続（論理削除・物理削除された利用者の行は表示しない／削除する）
取り込み原本（オブジェクトストレージ） 90日で自動削除
採点ジョブ 30日で削除（結果は ANSWER_LOGS に残る）
通知の送信リスト（オブジェクトストレージ） 7日で自動削除
ジョブキュー・トークン 終わったジョブは30日、期限の切れたトークン・再設定リンクは1日で削除
ログ（コンテナのログ） サーバーの中に1コンテナ200MBまで（古いものから消える）。長く残す必要が出たら Phase 2 でログの置き場所を決める

8. 非機能・セキュリティ設計

8.1 認証・権限

項目 設計
認証 アプリのログイン（S-01）。パスワードは8文字以上・英大小文字と数字を含む。パスワードは scrypt のハッシュだけを保存する。5回続けて失敗したら15分ロック
トークン アクセストークン（署名つき JWT）1時間、リフレッシュトークン7日（使うたびに替わる。ログアウト・削除・パスワード再設定で無効にする）
権限 DB のロール（learner・course_admin・system_admin）で判定。画面の出し分けだけでなく、APIでも必ず確認する
コース管理者 担当コースのデータだけ参照・操作できる
管理画面の入口 管理者のグループに入っている人にだけ、ヘッダーに「管理局へ」を表示
将来のSSO 社内のIDプロバイダー（OIDC）でのログインを追加する形で対応（Phase 3）

8.2 データ保護

項目 設計
通信 すべてHTTPS（TLS 1.2以上）。Caddy で HTTP を HTTPS に転送し、HSTS を付ける。DB とはローカル接続（インターネットを通らない）
保存 DB・オブジェクトストレージの暗号化の扱いは構築時に確認する（手順書）。パスワード・トークンはハッシュで保存
オブジェクトストレージ すべて非公開。api コンテナ経由または署名付きURLでのみ読み書き
AI 送ったデータがモデルの学習に使われないことを、さくらのAI Engine・Bedrock とも構築時に確認して記録を残す。アプリのログに説明文・プロンプトは出さない
学習者どうし 氏名・メールは見えない。ランキングはニックネームのみ
操作記録 管理者の操作（公開・削除・復活・ロール変更・CSV出力）を記録

8.3 性能・可用性

項目 目標
画面表示 通常2秒以内（DBの自動停止がないため、その日最初の操作も待たない）
択一の判定 1秒以内
説明の採点 30秒以内
稼働時間 業務時間内に使えること（パイロット期間は24時間保証なし）
バックアップ データベースアプライアンスの自動バックアップ（世代数は構築時に決める。prod は7日分以上）
全社展開 Phase 3 でサーバー・DBのプラン、API のコンテナの数（ロードバランサーを置くか）、WAF の要否、ワーカーの同時処理数を見直す
サーバーの更新 OS のセキュリティ更新を毎月行う（手順書）。更新のあとは /api/health と画面を確かめる

対象 アラームの条件 通知先

9. メッセージ設計

9.1 方針

  • 責めない。不正解・不合格・未達成に赤い警告色や強い言葉を使わない
