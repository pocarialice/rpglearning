## 2. システム方式設計

### 2.1 方式の選定理由

2026-10-27 に、AWS からさくらのクラウドへ切り替えた。AWS アカウントで Amazon Bedrock（全モデル）と AWS Lambda が使えなくなり、復旧の見込みが立たなかったため。

| 観点    | 判断                                                             |
| ----- | -------------------------------------------------------------- |
| データの置き場所 | さくらのクラウドは国内の事業者・国内のデータセンター。学習者の説明文を含め、すべてのデータを国内に置ける |
| 規模の変動 | パイロット約10名はサーバー1台で足りる。全社約1,000名では、サーバーのプランを上げるか、API のコンテナを増やす（Phase 3） |
| コスト   | 月額の固定費（サーバー・DB）が中心で、見通しが立てやすい。AI は使った分だけ（2.9） |
| 運用    | サーバーの OS は自分たちで更新する。アプリはコンテナにまとめ、`docker compose` だけで入れ替えられるようにする |
| 移し替えやすさ | DB・ファイル・メール・AI・ログインを「差し替え口」にしてあるため、AWS や別のクラウドにも移しやすい（詳細設計書 3.6〜3.10） |

### 2.3 サービス一覧

| サービス | 役割 | 主な設定 |
| --- | --- | --- |
| サーバー（さくらのクラウド） | アプリを動かす | Ubuntu。Docker Compose で `caddy`・`api`・`worker` の3つのコンテナを動かす。パケットフィルタで 80・443 だけ開け、SSH は管理者のIPアドレスからだけ受ける |
| Caddy（コンテナ） | HTTPS の終端 | Let's Encrypt の証明書を自動で取って更新する。HSTS を付け、本文は2MBまで |
| api コンテナ | 画面の配信・API・ログイン | 画面（HTML／CSS／JS）と `/api/*` を1つのドメインで出す。キャラクター画像はオブジェクトストレージから読んで返す |
| worker コンテナ | 時間のかかる処理と定期処理 | 採点・問題取り込みをジョブキュー（DB）から1件ずつ取り出して処理する。日次処理とメール送信を時刻どおりに動かす |
| データベースアプライアンス | 業務データ | PostgreSQL。自動バックアップを有効にする。サーバーとはローカル接続（スイッチ）でつなぎ、インターネットには出さない |
| オブジェクトストレージ | ファイル | S3 互換。バケットは取り込み原本（90日で削除）・キャラクター画像・通知の送信リスト（7日で削除）の3つ。すべて非公開。アップロードは署名付きURL |
| さくらのAI Engine | 抽出・採点・コメント生成 | OpenAI 互換の API。モデルは gpt-oss-120b。アカウントトークンで認証する |
| メール送信（SMTP） | 通知・招待・パスワード再設定・監視のお知らせ | 社内の SMTP サーバー、またはさくらのメールボックスなど。送信ドメインの認証（SPF・DKIM）を設定する |
| コンテナレジストリ | アプリのコンテナの置き場所 | GitHub Actions が置き、サーバーが取りに行く。非公開 |
| シンプル監視 | 死活監視 | `/api/health` を5分ごとに見て、応答がなければ管理者にメール |
| DNS | 独自ドメイン | ドメインが決まるまでは、さくらのクラウドのサーバーに付く名前で動かす |

### 2.4 コンテナの役割の分担

AWS 版の Lambda 4関数は、2つのコンテナにまとめた。中の処理（ルーティング・採点・抽出・日次処理）は AWS 版と同じものを使う。

| コンテナ | 起動のきっかけ | 処理 | AWS 版での担当 |
| --- | --- | --- | --- |
| `api`（`ROLE=api`） | 画面からのリクエスト | 画面の配信、API 全般、ログイン（4.11）。四肢択一の正誤判定、軽量モデルでのひとこと生成。採点・取り込みはジョブキューに入れる | CloudFront・API Gateway・`api-handler`・Cognito |
| `worker`（`ROLE=worker`） | ジョブキュー（DB）と時刻 | キーワード説明の採点、PDF・画像・テキストからの問題の抽出、日次処理、30分ごとのメール送信 | `grading-worker`・`import-worker`・`batch-runner`・SQS・EventBridge Scheduler |

- 1台で足りる間は、`api` と `worker` を同じサーバーで動かす。どちらも同じコンテナ（イメージ）で、環境変数 `ROLE` で役割を変える
- 採点は同時に2件、取り込みは同時に1件まで処理する（AI の使いすぎを防ぐ）

### 2.5 説明採点の非同期方式

採点は30秒近くかかることがあるため、受付と処理を分ける。画面は2秒ごとに結果を確認し、その間AIパートナーの待機演出を表示する（AWS 版と同じ）。

```mermaid
sequenceDiagram
  participant U as 学習者（ブラウザ）
  participant API as api コンテナ
  participant Q as DB（ジョブキュー）
  participant W as worker コンテナ
  participant AI as さくらのAI Engine
  participant DB as DB（業務データ）
  U->>API: POST /api/gradings（説明文）
  API->>DB: 採点を登録（状態：採点中）
  API->>Q: 採点のジョブを入れる
  API-->>U: 202 受付（ジョブID）
  Note over U: パートナーの待機演出を表示
  W->>Q: ジョブを取り出す（1秒ごとに確認）
  W->>AI: 採点を依頼（パートナーの性格を含む）
  AI-->>W: 点数・模範説明・不足観点・コメント
  W->>DB: 結果保存・復習段階更新・EXP加算
  loop 2秒ごと（最大30秒）
    U->>API: GET /api/gradings/{id}
    API-->>U: 状態（採点中 または 完了）
  end
  Note over U: 30秒を超えたら再試行を案内
```

### 2.7 環境構成

| 環境   | 用途               | 利用者        | サーバー・DB |
| ---- | ---------------- | ---------- | ------------------------- |
| dev  | 開発・動作確認、システムテスト・受け入れ確認 | 開発者・コース管理者（受け入れ確認） | サーバー1台・データベースアプライアンス1台（最小のプラン） |
| prod | 本番（パイロット→全社）     | 全利用者       | サーバー1台・データベースアプライアンス1台（Phase 3で見直し） |

1つのさくらのクラウドのアカウントの中で、リソース名の接頭辞とタグで環境を分ける。

- コストを抑えるため、検証用の stg 環境は作らない（2026-10-21 決定）。システムテストとコース管理者の受け入れ確認は dev で行う
- 受け入れ確認の間は dev に新しい版を入れず「凍結」する。確かめた版にタグを付けて prod に配置する（詳細設計書 11.1）
- prod への配置の直前に、必ず DB のバックアップ（控え）を取り、問題があれば戻せるようにする
- 全社展開（Phase 3）の前に、stg を作り直すかを見直す（10 未決事項 No.11）

- 命名規則：`rpg-{env}-{用途}`（例：`rpg-prod-db`）
- タグ：`rpg-learning`、`dev` または `prod`。請求はタグで環境ごとに集計する
- サーバーの API キーなどの秘密の値は、各サーバーの `.env` に置き、Git に入れない
- さくらのクラウドのリソースは構築手順書に沿ってコントロールパネルで dev → prod の順に作る。アプリ（コンテナ）は GitHub Actions が作ってレジストリに置き、サーバーで入れ替える。DB のテーブルはコンテナの起動時に自動で作る（マイグレーション）
- 配置のきっかけ：dev は GitHub Actions を `main` で手動実行したとき、prod は dev での受け入れ確認のあとタグ `release-YYYYMMDD-NN` を付け、承認者が GitHub で承認したとき（詳細設計書 第11章）

### 2.8 AIモデルの使い分け

AI の呼び出しは「差し替え口」（詳細設計書 3.6）を通し、環境変数 `AI_PROVIDER` で呼び出し先を切り替える。当面はさくらのAI Engine を使い、Amazon Bedrock が使えるようになりしだい Bedrock に戻す。

| 用途                     | さくらのAI Engine（当面） | Amazon Bedrock（戻したあと） | 呼び出し元            |
| ---------------------- | ----------------- | ---------------- | ---------------- |
| 問題・キーワードの抽出            | gpt-oss-120b | Claude Sonnet | worker（取り込み）  |
| キーワード説明の採点             | gpt-oss-120b | Claude Sonnet | worker（採点） |
| 四肢択一の解説コメント・パートナーのひとこと | gpt-oss-120b | Claude Haiku  | api    |
| 四肢択一の正誤判定              | AI不使用 | AI不使用             | api    |

- さくらのAI Engine は国内のデータセンターで推論する（さくらインターネットの説明）。送ったデータの扱い（学習に使われないこと）は構築時に利用規約で確認し、記録を残す
- gpt-oss-120b は PDF・画像をそのまま読めない。そのため当面は、**PDF は文字を取り出してから渡し、画像の取り込みは使えない**（管理者には「テキストかPDFで取り込んでください」と出す）。文字のない（スキャンした）PDF も取り込めない。Bedrock に戻すと、PDF・画像をそのまま読めるようになる
- 採点の質は Claude より下がる可能性がある。パイロットの前に、過去問を使って採点の結果を Claude（AWS 版の試験の結果）と見比べ、合格の基準（60点）や指示文を見直すかを決める（10 未決事項 No.12）
- Bedrock に戻すときのモデルIDは、そのときに東京リージョンで使えるものを確かめる（AWS 版の外部設計書 2.8 の方針。推論プロファイルを使うかは未決事項 No.2）

### 2.9 月額コスト試算（パイロット10名）

| データベースアプライアンス（PostgreSQL・最小のプラン） | 構築時に確認 | 構築時に確認 | 自動バックアップあり |

| コンテナレジストリ・シンプル監視・DNS | 構築時に確認 | （prod と共用） | |

**さくらのAI Engine の内訳（prod）**

| 用途 | 月額 | 前提 |
| --- | --- | --- |
| 説明採点 | 約120円 | 1人1日5回 × 22日 × 10名。1回あたり入力3,000・出力800トークン |

| 問題取り込み | 約50円 | 月150ページ・300問 |

- gpt-oss-120b の単価は、入力1万トークンあたり0.15円・出力1万トークンあたり0.75円（税込、従量課金プラン）。月3,000回までの無料枠があるが、無料のプランは上限を超えると遅くなり自動で従量課金に切り替わらないため、prod は従量課金のプランにする
- AWS 版（2026-10-21 試算）は合計 約6,900円／月（Bedrock の Claude と Aurora の自動停止が中心）。さくら版は AI がほぼ無料に近くなる代わりに、サーバーと DB が固定費になる
- 利用回数は仮置き。説明問題を多く解くほど AI の費用は増える（それでも月数百円の規模）

### 3.6 AIパートナー設計

#### 3.6.1 キャラクター定義

| 項目          | 励まし型 `encourage`       | 論理型 `logic`                   | ライバル型 `rival`             |
| ----------- | ---------------------- | ----------------------------- | ------------------------- |
| 初期名         | ミナ                     | セージ                           | レン                        |
| 性格          | 明るく寄り添う。小さな前進を見つけて褒める  | 冷静で分析的。根拠と効率を重視する             | 負けず嫌いで競争心をあおる。ただし相手を責めない  |
| 口調          | くだけた話し方「〜だね」「〜しよう」     | です・ます調「〜です」「〜が効率的です」          | 少し強気「〜だな」「次は負けないぞ」        |
| 採点コメントの組み立て | 良い点 → 足りない観点を1つ → 応援   | 点数の根拠 → 足りない観点 → 次にやること       | 点数への反応 → 足りない観点 → 挑戦の呼びかけ |
| ホームのひとこと例   | 「昨日より3問多く解けてるよ。今日もいこう」 | 「今日の復習は5問です。説明問題から始めるのが効率的です」 | 「今週はまだ俺の方が上だな。追いつけるか？」    |
| 紋章の枠の色      | `gold-ink`             | `teal`                        | `crimson`                 |

**AIへの共通指示（全キャラクター）**

- 発言は2〜3文まで
- 説教・減点の言い方・人格を否定する表現はしない
- 不合格のときも、次にやることを1つ示して終える

#### 3.6.2 名前の入力ルール

| 項目     | ルール                                                   |
| ------ | ----------------------------------------------------- |
| 入力する画面 | S-09（初回は必須の流れの中で表示）                                   |
| 文字数    | 1〜10文字                                                |
| 使える文字  | ひらがな・カタカナ・漢字・英数字。記号と絵文字は不可                            |
| 未入力のとき | 初期名（ミナ・セージ・レン）を使う                                     |
| 変更     | いつでも変更できる。キャラクターを変えると名前は新しいキャラクターの初期名に戻る（以前の名前は保持しない） |
| 表示範囲   | 本人の画面だけ。ランキングなど他の人には出さない                              |

#### 3.6.3 紋章（キャラクター画像）

| 項目      | ルール                                               |
| ------- | ------------------------------------------------- |
| 画像      | 1キャラクターにつき1枚（表情1種）。将来は「通常・喜び・考え中」などの表情を追加できる作りにする |
| 形式      | PNG または WebP、正方形、512×512px 以上、透過背景を推奨、2MBまで       |
| 表示      | `gd-sigil` の円の中に画像を表示し、枠の色で性格を示す                  |
| 画像がないとき | 名前の頭文字を明朝で表示する（デザインシステムの既定の表示）                    |
| 差し替え    | S-14 でシステム管理者が行う。差し替えると全学習者の表示が変わる                |

| まとめて処理 | 各行のチェックボックスと、見出しの「表示している問題をすべて選ぶ」で問題を選び、「選んだ問題を公開する」（primary。公開できる形の下書き・要確認だけ公開し、ほかはそのまま）・「選んだ問題を削除する」（下書き・要確認は削除、公開済みは出題から外し解答の履歴は残す）。どちらも確認ダイアログあり。一覧を読み直したら選択は外れる |
| 修正（ダイアログ） | 下書き・要確認の行だけ「修正する」を出す。ダイアログで問題文・選択肢4つ・正解・解説・キーワード（最大3つ）を修正し、横に学習者エリアでの見え方（答える前／答えたあと）を入力に合わせて出す。「保存して次へ」「公開して次へ」（primary）「削除する」（確認ダイアログあり）のあと、一覧の次の下書き・要確認へ進み、最後まで見たら閉じる。「前へ」「次へ」で移れる（保存していない修正があるときは、もう一度押したら移る） |

### 4.3 出題ルール（F-03、F-05）

| 順 | 出題対象           | 条件                          |
| - | -------------- | --------------------------- |
| 1 | 今日の復習（期限切れを含む） | 復習予定日が今日以前。予定日の古い順          |
| 2 | 未学習の問題         | 公開済みで、まだ解いていない問題。登録順        |
| 3 | 学習済みの問題        | 1と2がないとき。正答率の低い順（復習段階は変えない） |

- 1回の冒険は10問。途中でやめてもそれまでの結果は保存する
- 四肢択一とキーワード説明は、出題対象の中で交互に出す。キーワードがない問題は択一のみ
- キーワード説明は1問につき1キーワードを出す（復習予定日の早いもの）

stateDiagram-v2

### 4.5 経験値・レベル（F-08）

| 行動                | 獲得EXP       | 復習のとき |
| ----------------- | ----------- | ----- |
| 四肢択一 正解           | 10          | 15    |
| キーワード説明 合格（60点以上） | 30          | 45    |
| デイリークエスト達成        | クエストごと（4.7） | 対象外   |
| 不正解・不合格           | 0（減らさない）    | 0     |

**レベル計算式**

- 次のレベルまでの必要EXP ＝ 100 × Lv^1.2（端数は切り上げ）
- 累計EXPは減らないため、レベルは下がらない
- 上限は設けない

| レベル | 次のレベルまでの必要EXP | そのレベルに到達する累計EXP |
| --- | ------------- | --------------- |
| 1   | 100           | 0               |
| 2   | 230           | 100             |
| 3   | 374           | 330             |
| 4   | 528           | 704             |
| 5   | 690           | 1,232           |
| 10  | 1,585         | 6,425           |
| 15  | 2,579         | 16,306          |
| 20  | 3,642         | 31,300          |
| 30  | 5,924         | 77,833          |

> 目安：1日に択一10問正解・説明1問合格・クエスト達成（約210 EXP）を続けると、1週間でLv5、1か月でLv9、3か月でLv16。

## 6. 定期処理設計

### 6.1 一覧

| ID   | 処理      | 実行タイミング              | DB       | 内容                                  |
| ---- | ------- | -------------------- | -------- | ----------------------------------- |
| B-01 | 日次処理    | 毎日 0:00              | 使う       | クエストの割り当て、継続バッジの判定、物理削除、その日の通知内容の作成 |
| B-02 | ランキング締め | 毎週月曜 0:00（B-01の中で実行） | 使う       | 前週の順位を確定して履歴に保存                     |
| B-03 | メール送信   | 毎日 6:00〜22:00 の30分ごと | **使わない** | その時刻の送信リストをオブジェクトストレージから読み、SMTPで送る            |

```mermaid
gantt
  title 定期処理のスケジュール（Asia/Tokyo）
  dateFormat HH:mm
  axisFormat %H:%M
  section 毎日 DBを使う
  日次処理 クエスト更新・物理削除・通知準備 :a1, 00:00, 15m
  section 毎週月曜 DBを使う
  ランキング締め・リセット 日次処理の中で実行 :b1, 00:00, 15m
  section 毎日 DBを使わない
  メール送信 30分ごとの送信枠 :c1, 06:00, 16h
```

### 6.2 メール送信の方式

学習者が送信時刻を選べるため、メールは1日に何度も送る。送信の処理を軽く・やり直しやすくするため、次の方式にする（AWS 版で DB の自動停止と両立させるために決めた方式を、そのまま使う）。

1. B-01（0:00）で、通知オンの学習者ごとに「送信時刻・宛先・復習数・クエスト」を作る
2. 送信時刻ごとのファイル（例：`notify/2026-10-20/0730.json`）にしてオブジェクトストレージに置く
3. B-03（30分ごと）は、その時刻のファイルだけを読んで SMTP で送る。DBにはアクセスしない

- 0:00より後に通知設定を変えた場合は、翌日の送信から反映する（S-10に注記を表示）
- 送信に失敗した宛先は1回だけやり直し、結果をログに記録する
- 定期処理は worker コンテナが時刻（Asia/Tokyo）を見て動かす。同じ枠を二重に動かさないよう、動かした枠を DB に記録する。worker が止まっていた日は、起動したときにその日の日次処理を動かす

### 6.3 処理ごとのルール

| 処理        | ルール                                             |
| --------- | ----------------------------------------------- |
| クエストの割り当て | 4.7 のとおり。前日の未達成クエストは残さない                        |
| 継続バッジ     | 前日に1問以上解答していれば連続日数を1増やす。していなければ0に戻す（バッジは取り消さない） |
| 物理削除      | 削除予定日を過ぎた利用者の学習履歴をすべて削除する（ログインの記録も一緒に消える）。期限の切れたトークン・再設定リンクも消す      |
| ランキング締め   | 前週分の順位を履歴に保存し、今週の集計を0から始める                      |
| 失敗時       | 30秒ごとに最大3回まで試す。それでも失敗したらシステム管理者に監視のお知らせメールを送る（5.6）   |
